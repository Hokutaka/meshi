# 要件定義 — meshi

- 文書バージョン: 0.1 (draft)
- 対象: 個人用 Android ネイティブ家計簿
- 状態: 設計案（実装済みを意味しない）

## 1. 目的

ユーザーが面倒に感じず継続して家計を記録できることを最優先とする。記録は支出・収入を対象とし、食事だけに限定しない。商品・明細の入力は任意とし、取引単位の簡易入力と共存させる。

## 2. 原則

1. **最小入力**: 金額、分類（必要なら初期値）、日時（既定は現在）だけで登録できる。
2. **詳細化は任意**: 後からメモ・店舗・商品明細を追加でき、マスタ登録を強制しない。
3. **合計の正本は取引**: 取引合計と明細は別管理。明細追加で過去の総額を勝手に変更しない。
4. **オフライン完結**: 全記録・集計・検索・復元はネットワークなしで利用できる。
5. **プライバシー**: アカウント、広告、追跡 SDK、アクセス解析、通信権限を持たない。
6. **耐久性と復旧性**: DB のスキーマ移行と、端末から独立した暗号化バックアップを提供する。
7. **最小権限**: 不要な Android 権限は宣言せず、ファイルアクセスは Storage Access Framework の選択操作に限定する。

## 3. 機能要件

### P0 — 初回実用版で必須

- FR-001 支出・収入を正の整数円の金額と取引種別で登録できる。0円や負の金額は基本的に拒否する。
- FR-002 取引にローカルの日付、発生日時、カテゴリーを指定できる。日時の初期値は現在とする。
- FR-003 店舗名、メモ、商品明細が未入力でも保存できる。
- FR-004 履歴を日付順に閲覧し、編集・削除できる。削除には誤操作対策を設ける。
- FR-005 月次の収入合計・支出合計・差引を、取引の正本金額から計算できる。
- FR-006 カテゴリーを登録・変更できる。記録済み取引の参照を破壊するマスタ削除は制限する。
- FR-007 アプリ専用領域に暗号化して永続保存する。鍵はアプリの平文設定ファイルには保存しない。
- FR-008 アプリロックを提供し、生体認証または端末認証を使える。再認証タイミングは明文化する。
- FR-009 暗号化バックアップをユーザー指定ファイルに出力・復元できる。復元前に形式・バージョン・整合性を検証する。
- FR-010 DBスキーマの移行に失敗したら、勝手に破壊的再作成せずエラーにする。
- FR-011 署名済みリリース APK を GitHub Releases から入手でき、同一署名で上書き更新できる。

### P1 — 日常運用を改善

- FR-101 任意の購入明細を追加できる。明細ごとに名称・金額・カテゴリーを持てる。
- FR-102 明細なし、部分明細、完全明細のいずれも許容する。
- FR-103 商品マスタに名称と既定カテゴリーを登録できる。商品マスタを使わない自由入力も可能。
- FR-104 よく使う取引をテンプレート化し、適用時に金額・分類を編集できる。
- FR-105 取引を店舗・カテゴリー・期間で検索・集計できる。
- FR-106 バックアップと復元の動作確認を案内する。

### 将来検討（初回は設計・実装を確約しない）

- 口座、支払方法、資金移動、残高管理
- 複数通貨、税・割引・返品の細分化
- サブスクリプションと定期取引
- レシートOCR、レシート画像、ウィジェット
- 商品ごとの価格履歴分析
- データの複数端末同期（オフライン専用方針を再検討した場合のみ）

## 4. データと集計のルール

- 取引の金額は **JPY の整数（Long）** で保存。取引種別（income / expense）を別フィールドに置く。
- 取引ID、明細ID、カテゴリーID、商品IDは安定した一意識別子を使用する。
- 取引の合計を月次サマリーの唯一の集計元とし、明細を別途加算して二重計上しない。
- 支出の明細金額は負数不可。支出取引では `sum(item.amountYen) <= transaction.totalYen` を満たすこと。編集時もトランザクションとして検証する。
- 明細のない残額は `totalYen - sum(item.amountYen)` で求め、**未入力額**として取引カテゴリーへ割り当てる。明細カテゴリー別合計 + 残額 = 取引合計。
- カテゴリー集計で明細がない取引は、取引カテゴリーに全額割り当てる。
- 商品マスタの名前・カテゴリー・既定価格を変更しても、過去明細の名称・金額・分類は変更しない（スナップショット保持）。
- 返品・返金は、将来専用のドメイン操作で定義する。初期版では別の収入取引として記録可能だが、収支分析の意味が変わり得ることを明示する。
- 保存タイムスタンプは UTC の epoch または ISO 8601 相当で正規化し、家計簿上の取引日付は `YYYY-MM-DD` として独立保存。日付変更時も月次集計に反映する。
- 口座振替などを単純な支出／収入として混同しない（将来専用取引種別を導入）。

## 5. 非機能要件

### セキュリティとプライバシー
- NFR-001 **Release APK の最終 merged manifest に INTERNET 権限が存在しない**ことを CI で検査する。
- NFR-002 ローカルDB暗号化、Android Keystoreによる鍵の保護、アプリロックを設計・実装・テストする。
- NFR-003 外部に保存するバックアップは強度の十分なパスフレーズを用いた認証付き暗号化を行う。パスフレーズや暗号鍵はバックアップへ平文で格納しない。
- NFR-004 機密データを例外メッセージ、Logcat、クラッシュ解析、スクリーンショット用テスト成果物に書き込まない。
- NFR-005 Android バックアップ・端末移行設定を確認し、OSバージョン別の実機試験で意図しない平文コピーを避ける。
- NFR-006 root 化端末、OS 自体の侵害、画面を撮影される攻撃からの完全保護は保証しない。

### 品質
- NFR-101 通信がない状態で起動・閲覧・入力・集計・バックアップ・復元できる。
- NFR-102 クイック入力の主要経路は「起動後、金額入力＋最少タップ」で完結する。定量目標は UI 試作後に設定。
- NFR-103 DBマイグレーション、取引編集、部分明細、暗号化バックアップの往復と改ざん検知に自動テストを設ける。
- NFR-104 署名鍵紛失時の既存データ上書き更新不能リスクを明記し、鍵の保管・復旧手順を別途準備する。
- NFR-105 公開 Git リポジトリに実データ、秘密鍵、リリース用キーストアをコミットしない。

## 6. リリース受け入れ基準

1. 機内モードで新規支出・収入を登録できる。
2. 同一日に複数取引がある場合も、一覧・編集・月次集計が正しい。
3. 明細なしでも取引全額が集計され、部分明細のカテゴリー集計も一致する（P1実装後）。
4. アプリ停止・再起動・OSのプロセス破棄後もDB内容が維持される。
5. 異なるDBスキーマバージョンからの移行が成功し、失敗時はデータを破壊しない。
6. 暗号化バックアップを新規インストール環境に復元でき、間違ったパスフレーズや改ざんは拒否される。
7. Release APK の権限・署名を検証できる。
8. 同一署名・増加した versionCode のAPK上書き更新後にもデータが残る。
9. 公開リポジトリに実データや秘密情報がないことを確認できる。

## 7. スコープ外の判断

実装段階で別途決定する: minSdk、SQLCipher/Room互換バージョン、アプリロックの再認証ポリシー、バックアップ暗号フォーマット、インポートのマージ/置換方式、リリース署名の保管・CI運用。これらは未決定のまま暗黙に実装しない。
